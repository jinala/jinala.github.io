Summary of WebRelate

WebRelate is a programming-by-example tool that combines data from the web with the structured data from spreadsheets. The tool takes as input a spreadsheet, some examples for the URLs that contain the desired web data, and examples of locations of the data within the webpages. Using these inputs, the tool produces a program that does the same transformation to the other rows in the spreadsheet. This program is itself a union of two different programs -- the first program learns a string transformation that can produce the URL strings for the remaining rows and the second program learns an extraction program that computes Xpaths (which identify nodes in HTML documents) that correspond to the desired data from these URLs.

Web IDE

You can play with WebRelate live at the following URL:
http://webrelate.azurewebsites.net

We also provide some sample spreadsheets to begin with. Note that this IDE is still at a beta stage and hence, it might be very brittle. For example, some of the webpages are very dynamic and hence, they might break our algorithms. For the experiments, we actually downloaded all the html files (hence they are static) and our algorithms work robustly on them. In future, we will try to overcome these issues.

To start with the Web IDE, you can import one of these sample spreadsheets by clicking on the Choose File button in the interface. Once the spreadsheet is loaded, the next task is to provide example URLs. You can do this in two ways: first, you can directly provide the URL as shown in demos 1 and 2. Second, you can enter a search query term and use a search engine (in this case bing search) to get a list of URLs and select one from them (demo 3). As mentioned in the paper (section 2 example 2.2), this second method is useful when URLs contain strings that cannot be derived from just the spreadsheet. Before you select the URL from the search results, make sure you click on an empty cell in the example row. This is the cell where the URL will be copied into.

The next step is to provide extraction examples. You can click on the cell that has the URL and then click on the load url button on the top. This will load the corresponding webpage in the right pane. (Note if your screen is too small, these two windows might overlap.) Now, click a new cell in the example row and highlight the desired data from the web page. Our system detects the HTML node that contains the highlighted region and sends it to the backend. Because of this, even if you select a part of the region in a HTML node, the entire node text will be copied.

Once the examples are provided, we can now start the learning. You can either click on the last extracted cell and click the fill all button or you can click on each item and fill them separately. This needs to be done in the following order: first, select the cell containing the search query (if any) and click on fill query button. Second, select the cell containing the URL and click on fill url button. Finally, select the data cell and click on fill data button. The time taken to complete this task can be significantly larger (couple of seconds depending on the internet speed) than the what is mentioned in the paper. This is because the paper only computes the time spent in doing the actual search where as in the demo most of the time is actually spent in getting the web pages. There is also the initial server setup time.

You can also check that the extracted data is actually correct by clicking on the other URLs and using the load url button. If at any time, you happened to do the wrong sequence of steps, the system can freeze. In those situations, it is better to reload the page and start again.

WebRelate benchmarks

We now discuss about the WebRelate benchmarks and show how you can reconstruct the graphs in the paper.

WebRelate is evaluated on 88 web-integration tasks. Because, the URL learning and the data extraction learning algorithms are pretty orthogonal, we evaluate them separately. So, these 88 benchmarks have 66 URL learning tasks and 88 extraction tasks.

Prerequistes

WebRelate software is implemented in C# and can only be run on a Windows machine and we are sorry that we cannot provide a precompiled Virtual machine. That said, you can always use a virtual machine even if you don't have a Windows machine. For example, a free tial version of Windows 10 virtual box can be found here.

We have only tested the system on a Windows 10 machine with VisualStudio 2015 and .NET framework 4.5.

Installing WebRelate benchmarks

The source code containing the benchmarks can be found here. Since WebRelate is a proprietary software, we are not able to provide the source code for the actual system.

There are two folders UrlsTests and ExtractionTests that contain the test cases. For example, UrlsTests/TestUrls.cs file contains all the URL test cases. Each test case has the inputData (data from the spreadsheet) and searchQuery terms (if present). The test case also has a list of expected outputs and we use this for verifying the results. When running a test case, the system starts by treating the first input as the given example and learns a program from this input-output example. Then, it runs the program on the remaining inputs. If all the outputs match, the test is done. Otherwise, the system adds the next unmatched input-output pair to the list of examples. The test is considered PASSED if it can learn the program eventually where the output is the total number of examples required and the time taken for the last iteration. The test is FAILED if the system cannot learn the program even with all the inputs, or it timesout (120s).

ExtractionTests/TestXpaths.cs has the test cases for data extraction learning. Here, the input is the inputData (data from the spreadsheets), searchQueries (if present) and the list of URLs (learned from the previous step). The outputs are represented using the Xpaths of the Html nodes and when verifying the program, we check if the node generated by the learned program is same as the node generated by the expected Xpath.

You can clone and compile these folders. For example, you can compile the UrlsTests project by using the following commands:
cd UrlsTests/
<path to msbuild.exe> UrlsTests.csproj

This creats a UrlTests executable in the UrlsTests/bin/Debug folder. Similarly, you can also compile the ExtractionTests project.

In case, compiling this manually is difficult, we also provide an application installer that will directly install the executables for you. You can download that here. After downloading, double-click the Setup.msi file to start the InstallShield wizard. Just follow the prompts to install WebRelate and the benchmarks. These files will be installed in C:\Program Files\WebRelate\Setup.

Running benchmarks

At this stage, we assume you have installed the software using either of the two approaches. In order to enforce reproducibility of the results, we also provide the downloaded html files that were used during our evaluation. Some of the Xpaths used for verifying the tests are dependent on the webpage, so we highly recommend using these downloaded files. The zip of the files can be found in the google drive. Download and extract the files into a location on your machine.

Next, you need to configure the system to use this new location to the downloaded files. If you compiled the files manually,
Go to UrlsTests/bin/Debug
Open UrlTests.exe.config
Edit line 16 to put in the new location in the value for HtmlsFolder key.
Similary, update line 17 to a writeable location on your machine that will contain the outputs of the test runs.

Repeat the process again in ExtractionTests/bin/Debug. Please use the same values for both url tests and extraction tests.

If you used the application installer,
Go to C:\Program Files\WebRelate\Setup
Edit UrlTests.exe.config and ExtractionTests.exe.config similar to above.

Now, we can run the tests. Either approach should have a run.sh file (in the repository or the installed folder) that lists all the configurations we used in the experiment. The Url experiments have two configuration parameters -- different configurations of the layered search algorithm (section 4.2.2) and whether or not output-constrained ranking is enabled (section 4.2.3) and you can set these configurations when running the experiments.

For example, consider the command
UrlTests.exe --noresult $NUM_RUNS 1 1
Here, the --noresult argument will suppress the default nunit test output because the system directly outputs to the folder set by the user. The next argument is the number of times each test should be run. Since there is no randomness in the algorithms, running it once should be sufficient. But, if the reviewer wants to increase the confidence, they can increase the NUM_RUNS. The next argument is the layer_mode. 1 standes for L1 to L4, 2 stands for L2 to L4, 3 stands for L3 to L4 and 4 stands for only L4 configurations from section 6.1. The last argument is the ranking_mode. 1 enables the output-constrained ranking and 0 disables it. The default settings are layers L1 to L4 and using output-constrained ranking. The other configurations are only for comparison.

The above command will the run all the UrlTests with the given configurations. You can also run a single run using
UrlTests.exe --noresult --test=NAME $NUM_RUNS 1 1
where you can get the list of test names by running
UrlTests.exe --noresult --explore $NUM_RUNS 1 1

Most of these configurations will be quick to run. The only configuration that takes significantly longer time (about an hour) is UrlTests.exe --noresult $NUM_RUNS 4 1. You can comment this configuration out if you don't want to wait that long as it is only a comparison configuation.

Similarly, you can run Extraction tests by the following command (for example),
ExtractionTests.exe --noresult $NUM_RUN 1
The extraction algorithm has only 1 configuration parameter i.e. whether or not to use the output-constrained ranking algorithm (section 5.2.3) and that is set by the last parameter in the above command.

Looking at the outputs

When you run the above commands, the console prints out some outputs. It basically lists the current test that is run, whether or not it PASSED, and if it did then the number of examples used and the time spent. The outputs are also dumped to outputs folder that has been set before.

Producing plots in the paper

Finally, after running all the different configurations, you can use the ProduceGraphs.py file (present both in the repository as well as the installed program) to generate the graphs in the paper. The command to run this is
python ProduceGraphs.py < path to outputs folder >

This will produce a graphs folder under the outputs folder and there will be four graphs corresponding to figures 22(a), 22(b), 23, and 25.
